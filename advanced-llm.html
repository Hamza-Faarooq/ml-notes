Chapter 0-A
N-Gram Language Models
The statistical baseline before neural networks — why it existed, why it failed

Before Word2Vec and Transformers, the dominant approach to language modeling was N-gram models — counting word sequences from a huge corpus and predicting the next word purely from frequency tables. They are still used in spell-checkers, mobile keyboards, and as baselines.

The Markov Assumption

An N-gram model assumes the probability of a word depends only on the previous N−1 words (the Markov Property). This is a drastic simplification of reality — in the sentence "The president of India, who was elected last year, announced…", the verb "announced" depends on "president" 10 words back, violating any small-N Markov assumption.

Chain Rule → N-gram Approximation
Full Chain Rule:
P(w₁,…,wₙ) = ∏ᵢ P(wᵢ | w₁,…,wᵢ₋₁) // exact but intractable

Bigram (N=2) Approximation:
P(wᵢ | w₁,…,wᵢ₋₁) ≈ P(wᵢ | wᵢ₋₁)

Trigram (N=3) Approximation:
P(wᵢ | w₁,…,wᵢ₋₁) ≈ P(wᵢ | wᵢ₋₂, wᵢ₋₁)

Bigram Probability Estimate (MLE):
P(wᵢ | wᵢ₋₁) = Count(wᵢ₋₁, wᵢ) / Count(wᵢ₋₁)

Example: P("mat" | "sat") = 4/7 // "sat mat" appeared 4 times, "sat" 7 times
The Sparsity / Zero-Probability Problem

Any trigram not seen in training gets probability 0. Under the chain rule, one zero term makes the entire sentence probability 0. A test sentence like "the quantum computer revolutionized cryptography" crashes to probability zero if that exact trigram was never in your training data.

Smoothing (The Bandage)
Laplace (Add-1) Smoothing
P_smooth(wᵢ | wᵢ₋₁) = [Count(wᵢ₋₁, wᵢ) + 1] / [Count(wᵢ₋₁) + |V|]

// Adds 1 to every bigram count — even unseen ones get P > 0
// Problem: Hugely over-transfers probability mass to rare events

Kneser-Ney Smoothing (Industry Standard):
P_KN(w | wᵢ₋₁) = max(C(wᵢ₋₁,w) - d, 0) / C(wᵢ₋₁) + λ(wᵢ₋₁)·P_continuation(w)

// P_continuation(w) = how many distinct contexts w appears in (not raw frequency)
// "San Francisco" — "Francisco" has high raw freq but only 1 context (after "San")
// KN correctly gives it low continuation probability

Why N-gram Models Died (3 Reasons) (1) The vocabulary explosion: a trigram model over a 50K vocabulary needs up to 50K³ = 125 billion possible entries — impossible to store. (2) No semantic generalization: "I ate pizza" and "I consumed a pizza" are completely unrelated to an N-gram model. (3) Fixed context window: no matter how large N grows, you cannot capture dependencies 30+ tokens back. Transformers have no such limit.
🎯 Interview Q&A — N-gram Models
What is the fundamental difference between how N-gram models and Transformers handle long-range dependencies?
N-gram models operate under the Markov assumption — the future depends only on the last N−1 words. No matter how large you make N, long-range dependencies (antecedent-pronoun resolution 40 tokens back, for example) are invisible. Transformers use self-attention with a global receptive field: every token computes a weighted sum over ALL other tokens simultaneously. The attention weight between token i and token j is a learned function of their content, not constrained by distance. The O(N²) complexity is the price for this global awareness.
If N-grams are obsolete, why does your phone's autocorrect still use them?
Three practical reasons: (1) Latency — an N-gram lookup is a hash table O(1) operation; a Transformer forward pass is milliseconds. Autocorrect must respond in under 50ms. (2) Size — a Transformer model is hundreds of MB; the N-gram table for a phone keyboard is ~2MB. (3) Local context is sufficient for autocorrect — "I want to" → "eat/go/see" doesn't need 10,000 tokens of context, just the last 2-3 words. N-grams are still optimal when the task has short context, requires extreme latency, and must run on-device.
Chapter 0-B
Decoding Strategies — How LLMs "Choose" Words
Temperature · Greedy · Beam Search · Top-K · Top-P (Nucleus) · Repetition Penalty

After the transformer's LM head projects the final hidden state to a logit vector over the vocabulary (shape: V ≈ 50,000–150,000), we must sample one token. This decision is not just argmax — the entire character, creativity, and factual reliability of the model's output emerges from this single sampling step.

The Raw Logit → Probability Pipeline
Logit → Softmax → Sample
LM Head: z = W_head · h_last ∈ ℝ^V // raw logit vector (unnormalized)

Standard Softmax: p_i = exp(z_i) / Σⱼ exp(z_j)

With Temperature T:
p_i = exp(z_i / T) / Σⱼ exp(z_j / T)

T → 0: p_argmax → 1.0, all others → 0 (deterministic greedy)
T = 1: standard softmax distribution
T → ∞: p_i → 1/V for all i (uniform random — completely incoherent)
Greedy Search — The Naive Baseline

Pick the highest probability token at every step. Fast, deterministic, but produces dull, repetitive text and can get trapped in degenerate loops: "the the the the…"

Beam Search — Smarter but Costly
Beam Search (width B)
Maintains top-B partial sequences at every step.

Step 1: From start token, compute top-B candidates
Step 2: Expand each of B sequences → B×V candidates
Step 3: Keep top-B by sum of log-probabilities
Step 4: Repeat until all B beams hit EOS or max_length

Score = Σᵢ log P(wᵢ | w₁,...,wᵢ₋₁) [log for numerical stability]

Complexity: O(B × V × N) vs O(V × N) for greedy

// Used in machine translation (B=4-8)
// NOT used for open-ended generation (tends to produce safe, generic text)
Top-K Sampling
Top-K
1. Sort vocabulary by probability: p₁ ≥ p₂ ≥ ... ≥ p_V
2. Set p_i = 0 for all i > K (zero out the long tail)
3. Re-normalize: p_i ← p_i / Σⱼ≤ₖ p_j
4. Sample from the truncated distribution

Problem: K is fixed regardless of how "peaked" the distribution is.
If next word is obviously "Paris", K=50 still pollutes with 49 bad options.
Top-P (Nucleus) Sampling — The Industry Standard
Top-P / Nucleus Sampling (Holtzman et al. 2019)
1. Sort by probability descending: p₁ ≥ p₂ ≥ ...
2. Find smallest set S such that Σᵢ∈S pᵢ ≥ P (cumulative mass)
3. Zero out all tokens not in S
4. Re-normalize and sample

P=0.9 means: "keep the minimum set of tokens that together
account for 90% of the probability mass."

Peaked distribution (certain next word): S has 1-3 tokens → conservative
Flat distribution (many valid options): S has 100+ tokens → creative

// This is why Top-P adapts naturally to context — K does not.
Repetition Penalty
Repetition Penalty (Keskar et al. 2019)
z_i_penalized = z_i / θ if token i has already appeared in context
z_i_penalized = z_i otherwise

θ > 1 (e.g., 1.3): Divides logits of already-used tokens, making them less likely
Prevents: "The cat sat on the mat. The cat sat on the mat. The cat sat..."

🎯 Interview Q&A — Decoding
A user sets temperature=0 in the API. What mathematically happens? Why is it used for code generation?
At T→0, we divide all logits by ε→0. The largest logit becomes +∞, all others become −∞ relative to it. After softmax, exp(+∞)/[exp(+∞) + exp(−∞) + ...] → 1.0/1.0 = 1.0 for the top token, 0.0 for all others. The model always picks the argmax deterministically — equivalent to greedy search. This is used for code generation because code requires exact, reproducible syntax. "def compute_mean(x)" has one correct continuation: "(arr):" — not fifty creative options. Temperature=0 ensures the model always chooses the statistically most likely correct token, making outputs reproducible across runs (crucial for debugging).
Why does beam search produce "safe" text? Why is it not used for chat LLMs?
Beam search maximizes joint probability: it finds the sequence with the highest product of per-token probabilities. High-probability sequences tend to be generic, factually safe, and linguistically bland — the "average" of everything in training data. For a creative writing prompt, the highest-probability continuation is often "Once upon a time" regardless of context. Chat LLMs need diversity and personality. Additionally, beam search does not generate one token at a time — it must complete full sequences — making streaming (showing text as it generates) much harder. Nucleus sampling with T=0.7-1.0 gives the natural, human-like variance that makes chat feel alive.
Chapter 0-C
RoPE — Rotary Positional Embeddings
The positional encoding behind LLaMA, Qwen, Mistral, and every modern LLM

Every model since LLaMA (2023) uses RoPE instead of the original sinusoidal absolute positional encoding. If you only know the 2017 Transformer PE, interviewers will immediately know you haven't kept up with the literature. RoPE is one of the most beautiful mathematical ideas in modern deep learning.

Why Absolute PE Fails for Long Context

Original sinusoidal PE adds a fixed vector PE_pos to each token embedding. The model learns that "token at position 512 has this specific pattern." When you try to run the model on 8192 tokens at inference (trained only to 4096), positions 4097–8192 were never seen during training — the PE vectors are extrapolated into completely foreign territory. Performance collapses.

The RoPE Insight — Relative Distance via Rotation

RoPE encodes position by rotating the Query and Key vectors by position-dependent angles before the dot product. The critical mathematical property: the dot product Q·K encodes only the relative distance between positions, not absolute position.

RoPE — Mathematical Derivation
For a 2D subspace, at position m, we rotate vector [q₁, q₂] by angle mθ:

R(m,θ) = [[cos(mθ), -sin(mθ)],
[sin(mθ), cos(mθ)]]

Rotated query at position m: q_m = R(m,θ) · q
Rotated key at position n: k_n = R(n,θ) · k

Attention score:
q_m · k_n = [R(m,θ)·q]ᵀ [R(n,θ)·k]
= qᵀ R(m,θ)ᵀ R(n,θ) k
= qᵀ R(n-m, θ) k // R(a)ᵀ R(b) = R(b-a)

KEY: The result depends only on (n-m), the RELATIVE distance.
Token "bank" at position 100 relates to "river" at position 95
identically to how it would at positions 5000 and 4995.

In practice: d_model/2 rotation planes, each with its own θ_i:
θ_i = 1 / 10000^(2i/d) (same frequencies as sinusoidal PE)
RoPE Long-Context Extension (YaRN / RoPE Scaling)

If trained on 4096 tokens but need 32768 at inference, we compress the rotation angles so positions 0–32768 map into the angles the model has seen (0–4096). Several techniques exist:

Linear RoPE Scaling
Scale factor s = target_length / train_length (e.g., 32768/4096 = 8)

Modified base: θ_i' = θ_i / s = 1 / (10000 × s)^(2i/d)

Effect: rotations now span [0, 2π] over 32768 positions instead of 4096

YaRN (Yet Another RoPE extensioN): applies different scaling to
low-frequency vs high-frequency dimension pairs, preserving
short-range attention quality while extending long-range capacity.
💡
RoPE vs ALiBi vs Learned PE ALiBi (Attention with Linear Biases) adds a fixed negative bias proportional to distance directly to the attention scores — no learned PE at all. It generalizes even better to long context than RoPE but has slightly lower quality on short sequences. Learned absolute PE (GPT-2, BERT) is best for fixed-length tasks but completely fails out of distribution. RoPE is the sweet spot: theoretically motivated, strong at all lengths, and extensible.
🎯 Interview Q&A — RoPE
A researcher trains a model with RoPE on 4096 tokens. They want to double the context to 8192 at inference by just feeding a longer sequence. Will it work? What will happen?
It will partially work but degrade significantly. Tokens 4097–8192 will have rotation angles (mθ for m up to 8192) that the model has never seen during training — they are in a mathematically extrapolated region. Because the model's attention patterns were calibrated for rotation differences corresponding to distances up to 4096, any token pair with distance >4096 will have an attention score based on rotation angles the model never learned to interpret. The fix is to apply linear RoPE scaling: divide all θ_i by 2, so the full 8192 positions map into the 0–4096 angle range the model was trained on. YaRN does this more carefully per dimension.
What is the "Lost in the Middle" problem, and how does it relate to positional encoding?
Even with perfect long-context support from RoPE, research shows LLMs pay disproportionate attention to tokens near the beginning of context (the system prompt) and near the end (the most recent user turn), while effectively ignoring tokens in the middle. This is not primarily a positional encoding failure — it's an attention pattern bias learned during training where training documents naturally have their most important information at the beginning and end. The mitigation is re-ranking: put your most relevant retrieved RAG chunks at the very start and end of the context window, not buried in the middle.

Mixture of Experts (MoE) — Deep Dive

MoE replaces the single FFN in each transformer block with N "expert" FFNs plus a learned router network. Only the top-K experts are activated per token, keeping compute low.

MoE Forward Pass (Mixtral-style)
Standard block: output = FFN(x) // always runs the same FFN

MoE block:
Router: g(x) = Softmax(W_router · x) ∈ ℝ^N // scores for N experts
TopK: selected = argtop2(g(x)) // pick 2 experts
Gate weights: s₁, s₂ = renormalize(g(x)[selected])
Output = s₁ · FFN_1(x) + s₂ · FFN_2(x) // weighted sum

Capacity: each expert handles a limited # tokens/batch to prevent collapse
Load balancing loss: auxiliary penalty = α·N · Σᵢ fᵢ · Pᵢ
fᵢ = fraction of tokens routed to expert i (should be 1/N)
Pᵢ = average router probability for expert i
🎯 Interview Q&A — Open Models
Your team needs to deploy a multilingual customer service bot that handles both English and Hindi queries. Should you use LLaMA 3 8B or Qwen 2 7B? Justify architecturally.
Qwen 2 7B. The architectural reason is vocabulary efficiency: LLaMA 3 has a 128K token vocabulary which is optimized for English. Hindi words like "आप कैसे हैं" get tokenized into many subword pieces because Devanagari script was not the primary training focus. Qwen's 152K vocabulary explicitly includes CJK and South Asian script coverage, so each word tokenizes into far fewer tokens. Fewer tokens per query means: (1) shorter sequences, (2) less attention computation, (3) lower inference cost, and (4) better context utilization. The model also saw more high-quality multilingual training data. The choice is architectural, not just empirical.
Explain why Mixtral 8×7B can run at the speed of a ~12B model despite having 46B total parameters.
In MoE, "total parameters" ≠ "active parameters per forward pass." Each token only activates 2 out of 8 experts. The embedding lookup, attention layers, and routing logic are shared (the same ~6B parameters). Only 2 of the 8 FFN experts execute per token — each expert is ~7B/8 ≈ 875M parameters, and 2 of those are activated = ~1.75B FFN params active. Total active computation per token: ~12B effective parameters. The other 34B parameters sit in GPU memory loaded but idle during any given token's forward pass. This means FLOPs (speed) scale with active parameters, while knowledge capacity scales with total parameters — you get the best of both worlds.

1.1 The Pre-training Objective
Autoregressive Language Modeling Loss (Causal LM)
Given token sequence w₁, w₂, ..., wₙ, maximize the likelihood:

L(θ) = -1/N · Σᵢ₌₁ᴺ log P(wᵢ | w₁, ..., wᵢ₋₁; θ)

= Cross-Entropy averaged over all tokens

At token i, the model only sees w₁,...,wᵢ₋₁ (causal mask enforces this).

Perplexity = exp(L) → a 30B model on Wikipedia achieves PPL ≈ 10-15
meaning: average "surprise" equivalent to choosing from 10-15 words
1.2 The Scaling Laws (Chinchilla)

The most important empirical finding in LLM research: how should you distribute your compute budget C between model size N and training data D?

Chinchilla Scaling Laws (Hoffmann et al., DeepMind 2022)
Compute budget: C ≈ 6ND (FLOPs for N parameters, D tokens)

Optimal allocation for a fixed compute budget C:
N_opt ∝ C^0.5
D_opt ∝ C^0.5

Rule of Thumb: D_opt ≈ 20N
LLaMA 3 8B → optimal on ~160B tokens
LLaMA 3 70B → optimal on ~1.4T tokens

Pre-Chinchilla mistake: GPT-3 (175B params, 300B tokens) was severely undertrained.
A 70B model trained on 1.4T tokens outperforms GPT-3 at 1/2.5 the inference cost.
💡
Why Chinchilla Changed the Industry Before Chinchilla (2022), everyone assumed "bigger model = better." GPT-3 used 175B parameters but only 300B tokens — ratio of 1.7 tokens/param. Chinchilla showed the optimal ratio is ~20 tokens/param. The same compute budget that produced GPT-3 would instead produce a ~70B model trained on 1.4T tokens, with significantly better downstream performance. This is why LLaMA 3 70B approaches GPT-4 on many benchmarks despite being 2.5× smaller — it was trained properly according to scaling laws.
1.3 Data Curation

The quality of pre-training data is arguably more important than model architecture. Modern pipelines remove duplicates, filter quality, and balance domains:

1
Raw Collection

Common Crawl (~1PB of web text), GitHub code (~800B tokens), Wikipedia, arXiv, books. Llama 3 used ~15T tokens total.

2
Deduplication

MinHash locality-sensitive hashing identifies near-duplicate documents. Exact dedup removes training/test set contamination that inflates benchmarks.

3
Quality Filtering

Heuristic rules (line length, symbol ratios, language detection). FastText classifiers trained on curated "good" text (Wikipedia quality). C4 uses "ended with a period" as a proxy for coherent text.

4
Domain Mixing

Manual or learned mixing ratios: 67% web text, 15% code, 8% books, 5% scientific papers, etc. Data mixture ratios are a key research frontier.

1.4 Emergent Abilities

Emergent abilities are capabilities that appear suddenly at a certain scale threshold — they score near-zero below the threshold and high above it. Examples: arithmetic at 7B+ params, multi-step reasoning at 50B+ params, few-shot chain-of-thought at 100B+.

⚠️
The "Emergence" Debate (2023) Schaeffer et al. (Stanford 2023) argued that emergent abilities are an artifact of discontinuous evaluation metrics (e.g., exact-match accuracy), not a real phase transition. If you plot performance with continuous metrics (log-prob of the correct answer), the improvement is smooth and predictable. The "emergence" is in the measurement, not the model. This remains debated — know both sides for interviews.
🎯 Interview Q&A — Pre-Training
Your company has a budget of 10^23 FLOPs for training. According to Chinchilla, how should you allocate between model size N and data D?
Chinchilla says N_opt and D_opt both scale as C^0.5. If C = 10^23 FLOPs, then N_opt ∝ (10^23)^0.5 ≈ 3×10^11 = 300B parameters, and D_opt = 20N ≈ 6T tokens. But practically: this would require ~1200 A100s for 3 months just for training passes. A real company at this budget would likely choose N=70B trained on 1.4T tokens first, validate the scaling curve, and only commit to 300B if the scaling law predictions hold. The key insight is: never make a 300B model with only 500B tokens of data — that's the pre-Chinchilla mistake.
Why does the order of training data matter? If you shuffle all 15T tokens randomly, would the model perform differently than if you present web data first, then code, then books?
Yes, significantly. Curriculum learning effects are real in LLM pre-training. Key concerns: (1) Catastrophic forgetting — if you train on 14T web tokens and then on 1T code tokens, the model's web knowledge degrades. This is why you interleave throughout. (2) Learning rate schedules are calibrated per epoch-equivalent — random shuffling spreads domain exposure evenly, which is generally preferred. (3) Cooldown phases — many recipes (like LLaMA 3) use a "cooldown" phase where high-quality data (curated web, textbooks) gets oversampled in the final 5% of training at reduced LR to sharpen the model. Data order at the end of training disproportionately affects final quality.
What is "training-test contamination" and why is it a critical data quality concern?
Training-test contamination occurs when documents from benchmark test sets (e.g., MMLU questions, GSM8K math problems) appear verbatim or near-verbatim in the pre-training corpus. The model effectively "memorizes" the answers without generalizing. Signs include: suspiciously high benchmark scores on exact-match tasks but poor performance on paraphrased versions; performance dropping significantly when new benchmark variants are released. Mitigation requires n-gram deduplication between training corpus and all known benchmarks. This is why responsible model cards include contamination analysis, and why "private test sets" are increasingly used to evaluate frontier models.

2.2 Loss Masking — The Critical Engineering Detail

During SFT training, the full (system + user + assistant) sequence is fed to the model. But we only want the model to learn to generate the assistant tokens, not to mimic the user's questions. We achieve this with prompt masking: set the loss to 0 for all non-response tokens.

SFT Loss with Prompt Masking
Full sequence: [system_tokens | user_tokens | assistant_tokens]

Mask: m_i = 0 if token i belongs to system/user portion
m_i = 1 if token i belongs to assistant response

Masked SFT Loss:
L_SFT = -1/Σmᵢ · Σᵢ mᵢ · log P(wᵢ | w₁,...,wᵢ₋₁; θ)

// Sum normalized over #response tokens, not total sequence length
// Without masking: model learns to "predict user questions" which
// wastes capacity and teaches wrong behavior (generating more questions)

🎯 Interview Q&A — SFT
Why is the gradient_accumulation_steps parameter important during SFT? What does it simulate?
Due to GPU memory limits, you can only fit a small per_device_train_batch_size (e.g., 2 sequences). But the gradient estimate from 2 sequences is extremely noisy. Gradient accumulation runs forward/backward passes for N micro-batches without calling optimizer.step(), then accumulates (sums) the gradients, and only updates weights once after N steps. This simulates a batch size of N × per_device_batch_size (e.g., 8 × 2 = 16) at the cost of N × longer training time per update. Larger effective batch sizes give lower gradient variance, more stable training, and allow higher learning rates. The math: E[∂L/∂θ] estimated from 16 samples is 2.8× lower variance than from 2 samples (variance ∝ 1/batch_size).
What is "sequence packing" and why is it critical for SFT throughput?
Most SFT datasets have variable-length examples (some instructions are 50 tokens, some are 2000). Without packing, every batch must be padded to the max length — a batch of 8 sequences where 7 are 100 tokens and 1 is 2000 tokens wastes 87.5% of compute on padding tokens. Sequence packing concatenates multiple short examples (separated by EOS tokens) into a single sequence of max_length, with the causal mask ensuring examples don't attend across boundaries. This maximizes GPU utilization and typically gives a 2–5× throughput improvement over naive padding.

RLHF — Reinforcement Learning from Human Feedback
The ChatGPT recipe — reward models, PPO, and KL divergence penalty

Even a perfectly instruction-tuned model can generate accurate but harmful, toxic, or manipulative text. RLHF (Ouyang et al., OpenAI 2022) introduced the recipe that turned GPT-3 into InstructGPT (ChatGPT's predecessor): train the model to maximize human preference using reinforcement learning.

3.1 The 3-Stage RLHF Pipeline
1
SFT Model (Starting Point)

Fine-tune the base LLM on human-written demonstrations. This gives us π_SFT — a decent assistant that knows the format but may still be harmful.

2
Reward Model Training

For each prompt x, generate two responses (y_w = preferred/won, y_l = rejected/lost). Human raters choose which is better. Train a separate model r_φ(x, y) to predict the preference score.

3
PPO Fine-Tuning

Use RL to update π_θ to maximize r_φ(x, y) subject to a KL constraint. The model learns to generate text humans prefer.

3.2 Reward Model — Bradley-Terry Model
Reward Model Training
Reward Model: r_φ: (prompt, response) → scalar score

Bradley-Terry Preference Model:
P(y_w ≻ y_l | x) = σ(r_φ(x, y_w) - r_φ(x, y_l))
= 1 / (1 + exp(-(r_w - r_l)))

Training Loss:
L_RM = -E_{(x, y_w, y_l)~D} [log σ(r_φ(x,y_w) - r_φ(x,y_l))]

Architecture: Take SFT model, replace LM head (V-dimensional) with
a scalar head (1-dimensional). Fine-tune on comparison data.
3.3 PPO with KL Penalty
RLHF PPO Objective
Objective to maximize:
J(θ) = E_{x~D, y~π_θ(·|x)} [r_φ(x,y)] - β·KL[π_θ(·|x) || π_SFT(·|x)]

Term 1: reward model score — maximize human preference
Term 2: KL divergence penalty — stay close to SFT model
β: balances exploitation vs divergence (typically β=0.1–0.5)

Without KL penalty: "Reward hacking" — the LLM learns to game the
reward model by generating text that scores high but is meaningless,
repetitive, or adversarial. (e.g., outputting "I love this!" to every
query because the RM rewards positive sentiment).

PPO Clip Objective:
L_CLIP = E[min(rₜ(θ)·Aₜ, clip(rₜ(θ), 1-ε, 1+ε)·Aₜ)]
where rₜ(θ) = π_θ(aₜ|sₜ) / π_θ_old(aₜ|sₜ) (importance sampling ratio)
🔥
Why RLHF is Painful in Practice RLHF requires 4 separate models in memory simultaneously: (1) the LLM policy π_θ being trained, (2) the frozen reference π_SFT for KL penalty, (3) the reward model r_φ, and (4) the value function V_ψ for PPO advantage estimation. For a 70B model, this is 4 × 140GB = 560GB VRAM minimum before activations. PPO also has notoriously tricky hyperparameter sensitivity — the clip ε, KL coefficient β, batch size, and learning rate all interact. A misconfigured run can collapse the model in hours.
Chapter 03-B
DPO — Direct Preference Optimization
No reward model. No PPO. Just direct fine-tuning on preferences.

DPO (Rafailov et al., Stanford 2023) is the most important algorithmic advance in LLM alignment since RLHF. It shows that the RLHF objective can be reformulated as a simple supervised classification problem — no reward model, no RL training loop, no PPO instability.

DPO Derivation Intuition

RLHF optimizes: max E[r(x,y)] − β·KL[π_θ || π_SFT]. It can be shown that the optimal policy satisfying this objective has a closed-form solution. DPO skips training the reward model and directly optimizes the closed-form policy using a binary cross-entropy loss on preference pairs.

DPO Loss — Full Derivation
RLHF closed-form optimal policy:
π*(y|x) ∝ π_SFT(y|x) · exp(r*(x,y)/β)

Rearranging: r*(x,y) = β·log[π*(y|x)/π_SFT(y|x)] + β·log Z(x)

Substituting into Bradley-Terry:
P*(y_w ≻ y_l | x) = σ(β·log[π*(y_w|x)/π_SFT(y_w|x)] - β·log[π*(y_l|x)/π_SFT(y_l|x)])

DPO Loss (replace π* with π_θ being trained):
L_DPO(π_θ; π_SFT) = -E_{(x,y_w,y_l)~D} [
log σ( β·log[π_θ(y_w|x)/π_SFT(y_w|x)]
- β·log[π_θ(y_l|x)/π_SFT(y_l|x)] )
]

Gradient effect:
∇ increases log π_θ(y_w|x) (preferred response becomes more likely)
∇ decreases log π_θ(y_l|x) (rejected response becomes less likely)
Weighted by how "wrong" the implicit reward currently is.

🎯 Interview Q&A — RLHF & DPO
What is "reward hacking" in RLHF, and give a concrete example of how it manifests?
Reward hacking occurs when the LLM learns to game the reward model rather than genuinely improve. The reward model is trained on finite human preference data and has blind spots. Classic example: if human raters prefer longer, more detailed responses, the reward model will assign high scores to length. The LLM learns to maximize length — generating verbose, repetitive text that scores highly on the reward model but is practically useless. Another example: raters prefer confident, assertive language, so the model learns to state falsehoods confidently. The KL penalty (β · KL[π_θ || π_SFT]) constrains the model from deviating too far from SFT behavior, limiting the severity of hacking.
DPO requires a reference model π_SFT. In production with LoRA adapters, how do you efficiently store both the training model π_θ and the frozen reference π_SFT without doubling VRAM?
With LoRA, the base model weights W_base are frozen and shared between π_θ and π_SFT. You load W_base once, then create two sets of LoRA adapters: the active adapter A_θ (being trained) and the reference adapter A_SFT (frozen, initialized from the SFT checkpoint). Forward passes for both π_θ(y|x) and π_SFT(y|x) reuse the same W_base but apply different adapters. This reduces the two-model memory requirement from 2 × full_model to 1 × full_model + 2 × adapter_params. For a 7B model with LoRA r=16, the two adapter sets are ~130MB each vs ~14GB for a full model copy — roughly 50× memory savings for the reference model.

LoRA — Low-Rank Adaptation
How ΔW = BA saves 99.6% of trainable parameters without meaningful quality loss
4.1 The Core Motivation

Full fine-tuning of a 70B model requires: 70B × 2 bytes (FP16) = 140GB for weights, plus 140GB for gradients, plus 280GB for Adam optimizer states (m, v per parameter). That's 560GB VRAM minimum — requiring 7× H100 80GB GPUs just to exist. LoRA reduces trainable parameters by 100–10,000×.

4.2 The Low-Rank Hypothesis

The key insight (Li et al. 2018, Aghajanyan et al. 2021): The weight updates ΔW learned during fine-tuning have intrinsically low rank. The "useful change" lives in a low-dimensional subspace of the full d×d weight space. This was measured empirically — the effective rank of ΔW is typically 4–64 even for models with d=4096.

LoRA Decomposition — Full Mathematics
Pre-trained weight: W₀ ∈ ℝ^{d×k} (frozen, not updated)

LoRA update: ΔW = B·A
B ∈ ℝ^{d×r} (randomly initialized from N(0, σ²))
A ∈ ℝ^{r×k} (initialized to zero so ΔW = 0 at start)
r ≪ min(d,k) (rank hyperparameter)

Modified forward pass:
h = W₀·x + (α/r)·B·A·x
α = scaling hyperparameter (usually set to α=r or α=2r)

Parameter count comparison (d=4096, k=4096, r=16):
Full ΔW: 4096 × 4096 = 16,777,216 parameters
LoRA BA: 4096×16 + 16×4096 = 65,536 + 65,536 = 131,072 parameters
Reduction: 131,072 / 16,777,216 = 0.78% (128× fewer trainable params)

At inference (zero overhead): W_merged = W₀ + (α/r)·BA

🎯 Interview Q&A — LoRA
Why is matrix B initialized to random N(0,σ²) but matrix A initialized to zero? What would happen if both were initialized randomly?
The initialization ensures ΔW = B·A = 0 at the start of training. This means the LoRA model starts behaving identically to the pre-trained base model — you don't perturb the carefully pre-trained weights at step 1. If both A and B were randomly initialized, ΔW = BA would be a random matrix that immediately corrupts the model's pre-trained knowledge before any gradient signal has guided the adaptation. The convergence curve would be much worse because the model must first "undo" the random perturbation before learning the actual task. The zero initialization is a trivial but critical stability trick.
You train a LoRA adapter with r=16 on a medical QA task. At inference you want zero extra latency. Walk me through the exact mathematical operation to merge the adapter.
The merged weight is W_merged = W₀ + (α/r)·B·A. Step by step: (1) Compute the adapter output: M = B·A where B ∈ ℝ^{4096×16} and A ∈ ℝ^{16×4096}, giving M ∈ ℝ^{4096×4096} — this is a regular matrix multiplication, O(4096×16×4096) FLOPs done offline once. (2) Scale: M_scaled = (α/r)·M = (32/16)·M = 2·M. (3) Add in-place: W₀ += M_scaled. Now W_merged replaces W₀. You can delete both A and B. At inference, the forward pass is just h = W_merged·x — exactly the same as without LoRA, zero extra latency.
Chapter 04-B
QLoRA — Quantized Low-Rank Adaptation
Fine-tuning 70B models on a single GPU via NF4 quantization + LoRA
4-B.1 The Memory Problem QLoRA Solves

LoRA reduces trainable parameter memory but the frozen W₀ must still be loaded in FP16. A 70B model = 140GB FP16 — requires 2× H100 80GB GPUs just to hold the frozen weights. QLoRA compresses W₀ to 4-bit, shrinking it to ~35GB, fitting on a single A100 80GB.

4-B.2 NF4 — NormalFloat4

NF4 is a custom 4-bit quantization scheme optimized specifically for neural network weights. It exploits the empirical observation that pre-trained weight tensors follow a roughly zero-mean normal distribution.

NF4 Quantization — The Math
Key insight: Neural network weights w ~ N(0, σ²)

NF4 uses 16 quantile levels that are equally spaced in probability space
under the standard normal CDF Φ:
q_i = Φ⁻¹(i/16) for i = 0, 1, ..., 15

Quantization: w̃ = q_{argmin_i |w - q_i|}

Why optimal for normal distributions? Uniform quantization wastes
precision on the rare extreme tails. NF4 puts more quantization levels
near 0 (where most weights concentrate) and fewer in the tails.

Double Quantization (QLoRA bonus):
The quantization constants (scales/offsets) are themselves quantized
from 32-bit → 8-bit, saving another ~0.5 bits per parameter.
Net: ~4.5 bits/param total (better than naive 4-bit).
4-B.3 QLoRA Forward Pass — Step by Step
1
Quantize W₀ (offline, before training)

Convert each weight tensor from FP16 (2 bytes/param) → NF4 (0.5 bytes/param). 70B model: 140GB → 35GB. This is done once before any training begins.

2
Initialize LoRA adapters in BF16

Create B ∈ ℝ^{d×r} and A ∈ ℝ^{r×k} in BF16 precision. These are the only trainable parameters. For all linear layers of a 7B model with r=16: ~83M params × 2 bytes ≈ 160MB.

3
Forward Pass (per layer)

Dequantize: W₀_NF4 → W₀_BF16 temporarily (done in SRAM, not stored back to VRAM). Compute: h = W₀_BF16 · x + (α/r)·B·A·x. Discard W₀_BF16 immediately. Only the NF4 version persists in VRAM.

4
Backward Pass (gradient only through adapters)

Gradients flow back through h = W₀·x + adapter·x. Because W₀ is frozen, ∂L/∂W₀ = 0. Only ∂L/∂A and ∂L/∂B are computed and stored. Adam optimizer states (m, v) for only 83M params ≈ 660MB vs 420GB for full FT of 70B.

5
Paged Optimizers (safety net)

GPU VRAM spikes during backward pass. NVIDIA Unified Memory allows overflow to CPU RAM. If a spike would cause OOM, optimizer states are paged to CPU DRAM and pulled back when needed. Prevents crashes, slight latency cost.

🎯 Interview Q&A — QLoRA
If the base weights are stored in 4-bit NF4 but the forward pass is in BF16, where exactly is the extra memory spent during each forward pass?
The temporary dequantized weight is created in L1/L2 cache (SRAM) of the GPU's streaming multiprocessors, not in VRAM (HBM). This is the key engineering insight: the dequantized W₀_BF16 only exists for the microsecond needed to compute the matrix multiplication for one layer. It is never written back to VRAM — it lives and dies in the SM cache. VRAM only ever holds the NF4 version. This is why QLoRA doesn't require 140GB VRAM for the 70B FP16 copy — the expensive memory is the persistent VRAM storage, not the transient compute buffer.
A colleague says "QLoRA trained models are worse than LoRA-trained models because of quantization noise." Is this true?
Empirically false. The QLoRA paper benchmarked QLoRA (4-bit base + BF16 adapters) against standard 16-bit LoRA and found performance parity on a wide range of benchmarks including MMLU and code generation. The intuition: the base model W₀ is frozen — it contributes no gradient signal. The only thing being learned is ΔW = BA, which is computed and stored in full BF16 precision. The quantization noise in W₀ is effectively a constant fixed offset to the model's activations, which the LoRA adapters can partially compensate for. The model learns to work within the quantized representation. Where quality can be degraded is if the quantization reduces the base model's ability to process certain inputs (very long documents, complex math) — in those cases, the LoRA adapter has less signal to work with.

from sentence_transformers import SentenceTransformer
import faiss, numpy as np
from transformers import pipeline

# ─── INDEXING PHASE (run once) ────────────────────────────────
documents = ["Your company documents..."]  # Load from PDFs/CSVs

# 1. Recursive splitter — preserves semantic boundaries
splitter = RecursiveCharacterTextSplitter(
    chunk_size=512, chunk_overlap=64,
    separators=["\n\n", "\n", ". ", " "]
)
chunks = splitter.create_documents(documents)

# 2. Bi-encoder embedding model
embedder = SentenceTransformer("BAAI/bge-large-en-v1.5")  # 1024-dim
embeddings = embedder.encode([c.page_content for c in chunks],
                              normalize_embeddings=True,  # for cosine sim
                              batch_size=64,
                              show_progress_bar=True)

# 3. FAISS IndexFlatIP (inner product = cosine if normalized)
dim = embeddings.shape[1]
index = faiss.IndexFlatIP(dim)
index.add(embeddings.astype(np.float32))

# ─── QUERY PHASE (per user request) ──────────────────────────
def rag_query(query: str, k: int = 3) -> str:
    # Embed query
    q_vec = embedder.encode([query], normalize_embeddings=True)
    
    # Retrieve top-K chunks
    scores, indices = index.search(q_vec.astype(np.float32), k)
    retrieved = [chunks[i].page_content for i in indices[0]]
    
    # Augment prompt
    context = "\n\n---\n\n".join(retrieved)
    prompt = f"""You are a helpful assistant. Answer ONLY using the context below.
If the answer is not in the context, say "I don't know."

Context:
{context}

Question: {query}
Answer:"""
    
    # Generate
    llm = pipeline("text-generation", model="meta-llama/Meta-Llama-3-8B-Instruct")
    return llm(prompt, max_new_tokens=256)[0]["generated_text"]

5-B.1 Embeddings — The Math of Semantic Search
Cosine Similarity — Why Not Euclidean Distance?
Cosine similarity: cos(θ) = (A·B) / (‖A‖·‖B‖) ∈ [-1, 1]

For unit-normalized vectors (‖v‖=1): cos(θ) = A·B (just dot product)

Why not L2 distance? Embeddings vary in magnitude. "cat" embedded as [0.1, 0.2] and
[1.0, 2.0] are the same direction — cos=1.0 — but L2 = 1.8.
Magnitude encodes frequency/confidence, not meaning.
Always L2-normalize embeddings before cosine similarity.

Inner product (un-normalized): captures both direction + magnitude
Used in ColBERT (late interaction) and dense retrieval with ANN.
5-B.2 HNSW — How ANN Search Actually Works

With 10M documents, computing cosine similarity to all 10M is O(N·d) per query — too slow for real-time. HNSW (Hierarchical Navigable Small World) builds a graph index that allows O(log N) approximate nearest neighbor search.

HNSW Algorithm — Graph Construction & Search
Graph Structure: Layer L (top): few nodes, long "highway" connections between them Layer 1: medium-density connections Layer 0: ALL N nodes, dense local connections

Insertion of new node v: Assign to layers 0..l where l ~ Geometric(m_L) [stochastic] l controls sparsity of upper layers

Search for query q: 1. Start at entry point in top layer L 2. Greedy search: move to neighbor with highest sim(q, neighbor) 3. When local optimum reached, drop down one layer 4. Repeat until Layer 0 reached 5. In Layer 0: return top-K among visited nodes

Why NOT O(N): You NEVER search all of Layer 0.
You enter Layer 0 at the node closest to q from Layer 1,
then only explore efSearch (=200) neighbors — not all N.

Total operations: M × log(N) where M=efSearch ~50-200
N=10M: HNSW ≈ 1200 ops vs Exact ≈ 10,000,000 ops
💡

Only exact search (FAISS IndexFlatIP) gives 100% recall — use only for small corpora (<100K docs).

Hybrid Search + RRF (Reciprocal Rank Fusion)
Hybrid Search — Combining Dense + Sparse (BM25)
Problem: Dense embeddings miss exact keywords (error codes, names, IDs).
BM25 misses semantic similarity. Use both, combine via RRF.

BM25 Score (term-frequency based):
BM25(q,d) = Σ_{w∈q} IDF(w) · TF(w,d)·(k₁+1) / [TF(w,d) + k₁·(1-b+b·|d|/avgdl)]
k₁=1.5, b=0.75 (document length normalization)

Reciprocal Rank Fusion:
RRF_score(d) = Σ_{r∈R} 1/(k + rank_r(d)) k=60 (constant)

R = {dense_ranking, bm25_ranking}
rank_r(d) = position of document d in ranking r (1-indexed)

Example: Doc A ranked #2 dense, #1 BM25:
RRF = 1/(60+2) + 1/(60+1) = 0.01613 + 0.01639 = 0.03252

🎯 Interview Q&A — RAG & Vector DBs
Your RAG system has 95% retrieval accuracy (correct doc in top-3) but the final answer accuracy is only 60%. What are the 3 most likely failure modes?
(1) "Lost in the Middle" — the correct chunk is retrieved (rank 2-3 of 3) but the LLM focuses on chunks at position 1 and 3 of the context, ignoring the middle. Fix: re-rank so the highest-scoring chunk goes first AND last. (2) Chunk boundary fragmentation — the answer spans two chunks (e.g., question refers to an entity defined in chunk N but answered in chunk N+1). The embedding scores each independently; the crucial linking chunk is never retrieved together. Fix: larger chunks or sentence-level re-chunking with entity co-reference. (3) LLM hallucination despite context — the model combines retrieved context with memorized (possibly wrong) knowledge. Fix: add explicit instruction "Answer ONLY from the provided context. If unsure, say 'I don't know'" and test with faithfulness evaluation (RAGAS).
Explain the RAGAS evaluation framework. How do you evaluate a RAG system without human labels for every query?
RAGAS evaluates 4 dimensions automatically using an LLM-as-judge: (1) Faithfulness: Does the answer contain ONLY information from the retrieved context? Computed by asking GPT-4 to verify each claim in the answer against the context. Score 0-1. (2) Answer Relevance: Does the answer actually address the question? GPT-4 generates N questions from the answer and checks if they match the original question via embedding similarity. (3) Context Precision: Are the retrieved chunks actually relevant? GPT-4 ranks retrieved chunks by relevance; precision@K measures how many truly relevant chunks are in the top positions. (4) Context Recall: Given a reference answer, what fraction of necessary information was retrieved? Decomposes reference into claims and checks which claims appear in context. These 4 metrics together create an automated evaluation loop that can run after every RAG pipeline change.
When should you use RAG vs Fine-tuning? Design a decision framework.
Use RAG when: (1) knowledge changes frequently (news, product updates, regulations) — reindexing is cheaper than retraining; (2) knowledge must be attributable — RAG can cite sources, fine-tuning can't; (3) knowledge is factual and discrete (documents, FAQs, manuals); (4) you have latency budget for retrieval (adds 50-200ms). Use fine-tuning when: (1) the task requires a different output format or style (e.g., medical summarization, legal clause extraction); (2) the required behavior is about HOW to reason, not what facts to use; (3) you need the knowledge baked into model weights for offline/edge deployment; (4) the domain vocabulary is so different that the base model tokenizer/embedder is ineffective. The ideal production system uses BOTH: fine-tune for style/format and capability, RAG for factual knowledge.

6.2 Chain-of-Thought — Why It Works

CoT dramatically improves performance on reasoning tasks for models above ~100B parameters. Below 7B, CoT sometimes hurts (the model generates incorrect chains that mislead the final answer). The key is that decomposing a problem into sub-steps distributes the cognitive load across more tokens — each token-prediction step only needs to make a small, tractable inference rather than one massive logical leap.

CoT — Mathematical Intuition
Standard prompting: P(answer | question) // one-step inference

Chain-of-Thought: P(answer | question, step₁, step₂, ..., stepₙ)

Each conditional P(stepᵢ | question, step₁,...,stepᵢ₋₁) is a simpler
distribution than P(answer | question) directly.

Information-theoretically: CoT trades token budget for accuracy.
The model spends O(n) tokens to decompose the problem but each
intermediate step is a much lower-entropy distribution → fewer errors
compound through the chain.

🎯 Interview Q&A — Prompt Engineering
Why does Chain-of-Thought work much better for large models (70B+) than small models (7B)? What does this tell us about emergent abilities?
CoT decomposes a complex reasoning task into a chain of simpler sub-steps. For CoT to help, each intermediate step must itself be correct — an incorrect reasoning step propagates and worsens the final answer. Small models (7B) don't reliably generate correct intermediate reasoning steps for complex arithmetic or logic problems. When the chain itself is wrong, it actively misleads the final prediction, performing worse than direct zero-shot answers. Large models (70B+) have sufficient capacity to generate accurate intermediate steps, so each step reduces uncertainty and error. The implication: "emergent reasoning" may not be a phase transition but rather the point where per-step accuracy crosses a threshold (~95%+) above which chain errors rarely compound. Below this threshold, CoT is net negative.

Why naive LLM serving wastes 60-80% of GPU memory, and how PagedAttention fixes it
7.1 The KV Cache Memory Problem

Every active generation request holds a KV cache in VRAM. Without careful management, this causes massive memory waste.

KV Cache Memory Per Request
For LLaMA 3 70B (L=80 layers, H=8 KV heads, d_k=128, FP16):

KV per token = 2 (K+V) × L × H × d_k × 2 bytes
= 2 × 80 × 8 × 128 × 2 = 327,680 bytes ≈ 320 KB/token

For a request generating 1000 tokens: 1000 × 320 KB = 320 MB

If serving 100 concurrent users: 100 × 320 MB = 32 GB
(Total VRAM for model weights 70B×2B = 140 GB)
Total VRAM needed: 140 + 32 = 172 GB → 3× H100 80GB

Naive allocation problem:
Pre-allocate max_seq_len tokens for each request (e.g., 4096)
100 users × 4096 × 320KB = 131 GB reserved, but only 32 GB used
Internal fragmentation wastes 75% of KV cache VRAM!
7.2 PagedAttention — The OS Virtual Memory Analogy

Kwon et al. (2023) borrowed the virtual memory paradigm from OS design. Instead of contiguous pre-allocated memory, KV cache is stored in non-contiguous fixed-size "pages" (blocks).

PagedAttention — Core Algorithm
Physical block: stores K,V for B tokens (block_size B=16 or 32)
Block table: maps (request_id, logical_block_idx) → physical_block_id

Allocation: Request starts → allocate 1 block (for first B tokens)
When block fills → allocate next block anywhere in physical memory
Blocks for one request need NOT be contiguous

Attention computation with paged KV: For query at position t, attention over all previous tokens:
A(t) = Σ_{b=0}^{⌊t/B⌋} Attn(q_t, K_block_b, V_block_b)
Gathers K,V from non-contiguous physical blocks using block table

Memory efficiency: Only allocates blocks as tokens actually arrive
No pre-allocation waste
Fragmentation ≤ 1 block per request (last partially-filled block)

Prefix sharing (Copy-on-Write): Two requests with same system prompt share physical blocks
Block table for both points to same physical block
Saves (system_prompt_tokens × 320 KB) per duplicate request
7.3 Continuous Batching

Traditional static batching: wait for B requests, run them all together to completion, then accept new requests. This is GPU-inefficient because short requests finish early but GPU idles waiting for the longest request.

Continuous batching (iteration-level scheduling): After each decoding step, check if any request has completed (hit EOS). Immediately insert a new request into the freed slot. The GPU is never idle between iteration steps. vLLM implements this natively — it's the primary reason vLLM achieves 20–24× higher throughput than naive HuggingFace serving.

AWQ vs GPTQ — Key Differences
AWQ — Activation-Aware Weight Quantization
Key insight: Not all weights are equally important.
1% of weight channels are "salient" — they have large activation magnitudes.
Quantizing these channels causes catastrophic accuracy loss.

AWQ approach:
1. Profile activation magnitudes on calibration set: s_i = E[|x_i|]
2. Scale salient weights BEFORE quantization: w̃_i = w_i · s_i
3. Compensate in inputs: x̃_i = x_i / s_i (no change to model output)
4. Now quantize w̃ — salient weights are now in a safer range

GPTQ: uses second-order Hessian information to find the optimal
quantization for each weight column, minimizing reconstruction error.
AWQ is typically faster to quantize and slightly higher quality.
Both achieve similar 4-bit quality (~97-98% of FP16).

7.5 Latency Optimization — The Full Stack
Inference Latency Breakdown
Total latency = TTFT + (N_tokens × TPOT)

TTFT (Time to First Token): = prefill_compute / GPU_throughput
Prefill processes all input tokens in parallel → fast (1 forward pass)
Bottleneck: compute-bound (matrix multiplications dominate)

TPOT (Time Per Output Token): = KV_cache_size / memory_bandwidth
One new token per step; loads entire KV cache from HBM each step
Bottleneck: memory-bandwidth-bound (not compute-bound!)

Optimizations:
Reduce TTFT: tensor parallelism (split matmuls across GPUs)
Reduce TPOT: GQA (4× smaller KV cache → 4× faster HBM reads),
quantization (half the bytes = double bandwidth efficiency),
speculative decoding (draft model proposes K tokens, verify in 1 step)
Speculative Decoding
Speculative Decoding — Parallel Draft Verification
Problem: Autoregressive decoding is inherently serial (1 token/step).

Solution:
1. Draft model (small, fast, e.g. LLaMA 3 1B) generates K tokens greedily
2. Target model (large, e.g. LLaMA 3 70B) verifies all K tokens in ONE
parallel forward pass (all K tokens at once, like prefill)
3. Accept tokens up to the first mismatch; reject the rest
4. Target model generates 1 corrective token at the rejection point

Speed gain: If draft accepts K tokens on average → K+1 tokens per target model call
instead of 1 token per call → up to K+1 speedup
Real-world: 2-4× speedup with acceptance rate ~70-80%

Correctness guarantee: The distribution of accepted tokens is identical
to the target model alone — no quality degradation (rejection sampling).
🎯 Interview Q&A — Serving & Quantization
Your 70B model serving system has high TTFT but low TPOT. What does this tell you, and how do you fix it?
High TTFT means the prefill phase (processing the input prompt) is slow. This is compute-bound — all input tokens must be processed in one forward pass. Causes: very long system prompts or user inputs, insufficient GPU compute, or inefficient attention implementation during prefill. Fixes: (1) Use FlashAttention-2 for IO-efficient attention during long prefills; (2) Tensor parallelism — split weight matrices across multiple GPUs to parallelize the heavy matmuls; (3) Prefix caching — if many requests share the same system prompt, cache its KV representations so they never recompute; (4) Reduce system prompt length. Low TPOT means the generation phase is fast — the KV cache fits comfortably in VRAM and memory bandwidth is sufficient. This is a good sign; your bottleneck is only in serving long-context inputs.
Explain tensor parallelism vs pipeline parallelism for serving a 70B model that doesn't fit on one GPU.
Tensor parallelism (TP, Megatron-style): Each weight matrix W is split column-wise or row-wise across N GPUs. For a 4096×4096 matrix with TP=4: each GPU holds a 4096×1024 shard. Every forward pass requires 1 AllReduce communication per layer (to sum partial results). Latency: each token pays AllReduce overhead, but N GPUs compute N× faster. Best for minimizing TPOT. Pipeline parallelism (PP): Split the model layer-by-layer — GPU 1 has layers 1-24, GPU 2 has layers 25-48, GPU 3 has layers 49-72, GPU 4 has layers 73-96. Each GPU passes activations to the next. Requires micro-batching to keep all GPUs busy (otherwise upstream GPUs idle while downstream processes). Best for fitting very large models. Real systems (vLLM, TensorRT-LLM) use TP within a node (fast NVLink) and PP across nodes (slower InfiniBand).
What is "prefix caching" in vLLM and why is it a killer feature for chatbots with long system prompts?
When multiple requests share an identical prefix (e.g., the same 1000-token system prompt defining the chatbot's persona), vLLM reuses the physical KV cache blocks for that prefix across all requests. The first request computes and stores the system prompt KV vectors. All subsequent requests using the same system prompt skip prefill for those tokens entirely — their KV blocks are already in the PagedAttention pool. Impact: for a 1000-token system prompt, this eliminates 1000 × 320KB × (N_requests - 1) of redundant computation and saves 1000 × 320KB × N_requests of VRAM. In a production chatbot with 1000 concurrent users all using the same system prompt, prefix caching reduces TTFT by ~70% and KV cache VRAM usage by ~40%. This is why enabling prefix_caching=True in vLLM is a near-zero-cost deployment optimization.

What is catastrophic forgetting, and how does LoRA and the KL penalty in RLHF/DPO protect against it?
Catastrophic forgetting occurs when fine-tuning on a narrow domain causes a model to lose its pre-trained general capabilities. Mathematically, gradient updates to minimize the new task's loss push weights in directions that increase the original pre-training loss. LoRA protects against this by design: the base weights W₀ are completely frozen — they cannot be modified by any gradient. Only the adapter ΔW = BA is updated. Even if ΔW is large, W₀ retains all general knowledge. After merging: W_merged = W₀ + ΔW. The model has both general knowledge (from W₀) and task-specific adaptation (from ΔW). The KL penalty in RLHF/DPO (β·KL[π_θ || π_SFT]) is the alignment equivalent: it penalizes the training objective if π_θ deviates too far from π_SFT in distribution. Large deviations would indicate the model is forgetting its SFT behavior. β controls the strength: β=0.5 gives strong constraint (safe but slow alignment), β=0.05 gives weak constraint (faster alignment but higher forgetting risk).
Walk me through what happens in VRAM, from the moment a RAG query arrives to the time the first token is generated, for a deployed vLLM system.
T=0ms: HTTP request arrives. Query text enters tokenizer (CPU). T+1ms: Tokenizer converts text to integer IDs. RAG retrieval: query embedding computed by SentenceTransformer (GPU), FAISS ANN search in HBM (300μs), top-3 chunks returned. T+50ms: Augmented prompt assembled ([system] + [context chunks] + [user query] → ~800 tokens). Prompt tokens transferred CPU→GPU (PCIe). T+51ms: Prefill phase begins. vLLM's PagedAttention allocates physical KV blocks (⌈800/16⌉ = 50 blocks × 320KB = 16MB allocated). All 800 input tokens processed in ONE parallel forward pass through all 32 layers. Each layer: W·x matmul (compute-bound, fast), stores K,V into allocated blocks. T+90ms: Prefill complete. Logits for last input token computed. Sampling (top-p) selects first output token. T+90ms: First token returned to user (TTFT=90ms). T+90ms+TPOT: Decoding loop begins. One token per step: load KV cache blocks from HBM, compute Q for new token, attend over all cached K,V (memory-bandwidth-bound, ~6ms/token on H100). New K,V block allocated if needed.
