Tensors
N-dimensional arrays that live on CPU or GPU — the foundation of everything

A torch.Tensor is PyTorch's equivalent of a NumPy ndarray, but with two critical additions: (1) it can live on a GPU, and (2) it can track gradient operations for automatic differentiation.

1.4 Broadcasting Rules
PyTorch Broadcasting (same as NumPy)
Two tensors are broadcastable if, for each trailing dimension: 1. They are equal, OR 2. One of them is 1, OR 3. One of them doesn't exist (pad with 1 on the left) Example: A: shape (3, 1, 4) B: shape ( 5, 4) B padded: (1, 5, 4) Result: (3, 5, 4) ← element-wise ops work! Common pattern in attention: Q: (batch, heads, N, d_k) K: (batch, heads, N, d_k) QK^T: (batch, heads, N, N) ← matmul broadcasts over batch, heads

🎯 Interview Q&A — Tensors
What is the difference between torch.view() and torch.reshape()? When does each fail?
view() requires the tensor to be contiguous in memory — the elements must be stored in a single block of memory in the expected order. After operations like .transpose() or .permute(), the tensor's strides change but the underlying memory doesn't move — it becomes non-contiguous. Calling .view() on a non-contiguous tensor raises: RuntimeError: view size is not compatible with input tensor's size. reshape() is a superset: it tries to share memory (returns a view) if possible, but silently copies data to a new contiguous block if necessary. Rule of thumb: after any permute/transpose, call .contiguous().view() or just use .reshape(). Knowing this matters for production: unnecessary copies from reshape() on large tensors can cause memory spikes.
You have tensors of shapes (32, 1, 512) and (1, 10, 512). What does adding them produce? Walk through the broadcasting rules.
Shape A: (32, 1, 512). Shape B: (1, 10, 512). Broadcasting rules — compare trailing dims rightward: dim 2: 512 == 512 ✓. dim 1: 1 vs 10 → one is 1, expand to 10 ✓. dim 0: 32 vs 1 → one is 1, expand to 32 ✓. Output shape: (32, 10, 512). Physically: A's "1" in dim 1 gets repeated 10 times; B's "1" in dim 0 gets repeated 32 times. The result is a (32, 10, 512) tensor where result[i,j,:] = A[i,0,:] + B[0,j,:]. This exact pattern appears in transformer cross-attention when computing QK^T across batch and heads.

Autograd & Computational Graphs
How PyTorch automatically differentiates any computation

PyTorch's autograd engine records every operation on tensors with requires_grad=True, building a dynamic computational graph. When you call .backward(), it traverses this graph in reverse, applying the chain rule at each node.

2.1 The Computational Graph
Computational Graph Visualizer

For: L = (x² + 3x).sum() where x = [2.0, -1.0]. Forward pass builds the graph; backward pass traverses it.

2.2 requires_grad, backward(), and .grad
Autograd — Complete Walkthrough
import torch

# 1. Create leaf tensor with gradient tracking
x = torch.tensor([2.0], requires_grad=True)
# x.grad_fn is None — leaf nodes have no grad_fn

# 2. Forward pass — PyTorch builds the graph
y = x**2 + 3*x   # y = x² + 3x, grad_fn=AddBackward0
z = y.sum()       # z = scalar, grad_fn=SumBackward0

# 3. Backward pass — traverse graph, compute gradients
z.backward()     # ∂z/∂x = 2x + 3 = 7 at x=2

print(x.grad)    # tensor([7.])  ← ∂z/∂x = 2(2) + 3 = 7 ✓

# IMPORTANT: grads accumulate! Must zero before each backward
z2 = (x**2).sum()
z2.backward()
print(x.grad)    # tensor([11.]) = 7 + 4 ← ACCUMULATED, NOT 4!
x.grad.zero_()  # reset before next step (optimizers do this)

# retain_graph: call backward() multiple times on same graph
z.backward(retain_graph=True)  # graph preserved, can call again

# Non-scalar backward: must provide gradient tensor
x = torch.randn(3, requires_grad=True)
y = x * 2  # vector output
y.backward(torch.ones_like(y))  # gradient of scalar = sum(y*v) where v=ones

# Detach: stop gradient flow (for metrics, logging, target networks)
x_detached = x.detach()         # new tensor, no grad_fn, shares data
loss_value  = loss.item()        # converts to Python float, detaches

# no_grad context: inference, val loop — no graph built, saves memory
with torch.no_grad():
    logits = model(X_test)       # ~40% faster, 0 memory for graph

# inference_mode: even faster than no_grad (for pure inference)
with torch.inference_mode():
    logits = model(X_test)
🔥
The Most Common Autograd Bug: Forgetting zero_grad() PyTorch accumulates gradients by design (useful for gradient checkpointing). If you call optimizer.step() without optimizer.zero_grad() first, gradients from previous batches are added to current ones. Your model trains on phantom data. Always: zero_grad() → forward() → loss.backward() → step(). The order matters: zero_grad() before forward, not after backward.

🎯 Interview Q&A — Autograd
Explain the PyTorch computational graph. Is it static or dynamic? What are the implications?
PyTorch builds a dynamic computational graph (also called "define-by-run" or eager execution). The graph is created during the forward pass — each operation on a tensor with requires_grad=True creates a new node with a pointer to the backward function and its inputs. The graph is rebuilt from scratch every forward pass. Implications: (1) Python control flow (if/else, for loops with dynamic lengths) works naturally — the graph reflects the actual computation path taken, so RNNs with variable sequence lengths, conditional computation, recursive networks all work without special handling. (2) Debugging is trivial: any Python debugger works, you can print tensors, add breakpoints. (3) Overhead: building the graph every forward pass costs time. This is why TF2/JAX with XLA compilation can be faster for fixed-shape computation. PyTorch addresses this with torch.compile() (TorchDynamo) which captures the graph and JIT-compiles it with TorchInductor.
What does .detach() do? Give three real use cases where you'd need it.
.detach() creates a new tensor that shares the same data/storage but is removed from the computational graph (requires_grad=False, grad_fn=None). Three critical use cases: (1) Logging loss values: always call loss.item() (internally detaches) to extract a Python float for your training logs. If you accidentally log the tensor itself, PyTorch keeps the entire computation graph in memory until that variable is deleted — causing memory leaks in long training runs. (2) Target networks in RL (DQN, etc.): the target Q-network provides labels for the online network. You don't want gradients to flow through the target network. Detach the target's output: target_q = target_net(next_state).detach().max(1)[0]. (3) GAN training: when training the discriminator, you compute D(G(z)) but don't want gradients flowing back into the generator. Detach the generator output: fake_imgs = G(z).detach() before passing to D.

3.1 The Dataset/DataLoader Architecture
The Abstraction Hierarchy
Dataset: defines HOW to access a single sample → __len__(): total number of samples → __getitem__(idx): returns (X, y) for sample idx DataLoader: wraps Dataset, handles: → Batching: collect n samples into (batch_size, ...) → Shuffling: random permutation each epoch → Parallelism: num_workers processes prefetch in parallel → Pinning: pin_memory=True copies to page-locked memory for faster CPU→GPU transfer → Collation: how to stack samples into a batch
Custom Dataset — The Template
from torch.utils.data import Dataset, DataLoader
import torch
import pandas as pd

class TabularDataset(Dataset):
    """Custom Dataset for tabular data"""

    def __init__(self, df: pd.DataFrame, target_col: str, transform=None):
        self.X = torch.tensor(df.drop(target_col, axis=1).values, dtype=torch.float32)
        self.y = torch.tensor(df[target_col].values, dtype=torch.float32)
        self.transform = transform

    def __len__(self) -> int:
        return len(self.X)      # REQUIRED: total number of samples

    def __getitem__(self, idx: int):
        x, y = self.X[idx], self.y[idx]
        if self.transform:
            x = self.transform(x)
        return x, y              # REQUIRED: return (features, label)

# Usage
train_ds = TabularDataset(df_train, target_col='label')
val_ds   = TabularDataset(df_val,   target_col='label')

train_loader = DataLoader(
    train_ds,
    batch_size=64,
    shuffle=True,          # True for train, False for val!
    num_workers=4,          # parallel data loading processes
    pin_memory=True,        # faster CPU→GPU transfer (use with CUDA)
    drop_last=True,         # drop incomplete last batch (for BatchNorm)
    prefetch_factor=2        # pre-load 2× num_workers batches ahead
)
val_loader = DataLoader(val_ds, batch_size=128, shuffle=False, num_workers=4)

num_workers Best Practices On a machine with 16 CPU cores: use num_workers=4–8 for I/O-bound datasets (images from disk), 2–4 for CPU-heavy transforms, 0 for pure in-memory tabular data (multiprocessing overhead hurts). On Windows: always use if __name__ == '__main__': guard or num_workers=0 (Windows multiprocessing fork issue). On Colab: use 2. Persistent workers (persistent_workers=True) keep worker processes alive between epochs, eliminating spawn overhead.
🎯 Interview Q&A — Data Pipeline
Your training is slow and the GPU utilization is only 30%. What are the likely causes and how do you fix them?
30% GPU utilization = the GPU is starving for data. Root causes in priority order: (1) num_workers=0: single-process data loading can't feed a fast GPU. Fix: set num_workers=4-8. (2) pin_memory=False: data transfer from pageable CPU memory to GPU is slow (requires kernel-level copies). Fix: pin_memory=True (allocates CPU memory in page-locked space, enabling DMA direct transfer). (3) Heavy CPU-side augmentation: complex transforms done serially before the GPU gets data. Fix: use multiple workers + consider GPU-side augmentation (NVIDIA DALI, Kornia, torchvision with GPU transforms). (4) Reading many small files: HDD random access bottleneck. Fix: pack data into HDF5/LMDB/WebDataset format (sequential reads are 10-100× faster). (5) Batch size too small: GPU underutilized because each forward pass is trivially small. Fix: use the largest batch that fits in VRAM (+ gradient accumulation if memory limited).

nn.Module — Complete Pattern
import torch
import torch.nn as nn
import torch.nn.functional as F

class MLPClassifier(nn.Module):

    def __init__(self, input_dim: int, hidden_dims: list, num_classes: int, dropout: float = 0.3):
        super().__init__()  # MUST call parent __init__

        # Register layers as class attributes → PyTorch tracks their parameters
        layers = []
        prev_dim = input_dim
        for h_dim in hidden_dims:
            layers.extend([
                nn.Linear(prev_dim, h_dim),
                nn.LayerNorm(h_dim),
                nn.GELU(),
                nn.Dropout(dropout)
            ])
            prev_dim = h_dim
        layers.append(nn.Linear(prev_dim, num_classes))
        self.net = nn.Sequential(*layers)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        """x: (batch_size, input_dim) → logits: (batch_size, num_classes)"""
        return self.net(x)

# Instantiate and inspect
model = MLPClassifier(input_dim=100, hidden_dims=[256, 128], num_classes=10)

# Count parameters
total  = sum(p.numel() for p in model.parameters())
trainable = sum(p.numel() for p in model.parameters() if p.requires_grad)
print(f"Total: {total:,} | Trainable: {trainable:,}")

# Inspect architecture
print(model)              # pretty print all modules
for name, param in model.named_parameters():
    print(f"{name}: {param.shape}")

Production Training Loop — Complete
import torch
import torch.nn as nn
from torch.optim.lr_scheduler import OneCycleLR

# Setup
device = 'cuda' if torch.cuda.is_available() else 'cpu'
model = MyModel().to(device)
optimizer = torch.optim.AdamW(model.parameters(), lr=1e-3, weight_decay=1e-4)
criterion = nn.CrossEntropyLoss()
scheduler = OneCycleLR(optimizer, max_lr=1e-2,
                        steps_per_epoch=len(train_loader), epochs=50)

best_val_loss = float('inf')
patience_counter = 0

for epoch in range(50):
    # ---- TRAIN ----
    model.train()
    train_loss, train_correct = 0.0, 0

    for X, y in train_loader:
        X, y = X.to(device), y.to(device)

        optimizer.zero_grad()         # 1. Clear old gradients
        logits = model(X)              # 2. Forward pass
        loss   = criterion(logits, y)  # 3. Compute loss
        loss.backward()               # 4. Backpropagate

        # 5. Gradient clipping (prevents exploding gradients)
        nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)

        optimizer.step()              # 6. Update weights
        scheduler.step()              # 7. Update LR (per step for OneCycle)

        train_loss += loss.item()
        train_correct += (logits.argmax(dim=1) == y).sum().item()

    # ---- VALIDATE ----
    model.eval()
    val_loss, val_correct = 0.0, 0
    with torch.no_grad():
        for X, y in val_loader:
            X, y = X.to(device), y.to(device)
            logits = model(X)
            val_loss += criterion(logits, y).item()
            val_correct += (logits.argmax(dim=1) == y).sum().item()

    val_loss /= len(val_loader)
    val_acc = val_correct / len(val_loader.dataset)
    print(f"Epoch {epoch+1} | Val Loss: {val_loss:.4f} | Val Acc: {val_acc:.4f}")

    # ---- EARLY STOPPING + CHECKPOINT ----
    if val_loss < best_val_loss:
        best_val_loss = val_loss
        patience_counter = 0
        torch.save({   # save checkpoint dict
            'epoch': epoch,
            'model_state_dict': model.state_dict(),
            'optimizer_state_dict': optimizer.state_dict(),
            'best_val_loss': best_val_loss,
        }, 'best_model.pt')
    else:
        patience_counter += 1
        if patience_counter >= 10:
            print("Early stopping triggered"); break

# Load best checkpoint
checkpoint = torch.load('best_model.pt', map_location=device)
model.load_state_dict(checkpoint['model_state_dict'])

5.3 Learning Rate Schedulers
LR Schedulers — When to Use Each
from torch.optim.lr_scheduler import *

# 1. Step Decay: reduce LR by gamma every step_size epochs
scheduler = StepLR(optimizer, step_size=10, gamma=0.1)

# 2. Cosine Annealing: smoothly decay to min_lr over T_max epochs
scheduler = CosineAnnealingLR(optimizer, T_max=50, eta_min=1e-6)

# 3. OneCycleLR: warmup + cosine decay — BEST for most tasks
scheduler = OneCycleLR(optimizer, max_lr=0.01,
                        steps_per_epoch=len(train_loader), epochs=50)
# Step this EVERY BATCH, not every epoch

# 4. ReduceLROnPlateau: reduce when metric stops improving
scheduler = ReduceLROnPlateau(optimizer, mode='min', factor=0.5, patience=5)
scheduler.step(val_loss)  # called with monitored metric

# 5. Linear Warmup + Cosine (transformers)
from transformers import get_cosine_schedule_with_warmup
scheduler = get_cosine_schedule_with_warmup(
    optimizer, num_warmup_steps=100, num_training_steps=total_steps
)
🎯 Interview Q&A — Training
What is the difference between Adam and AdamW? Why does it matter for transformers?
The difference is in how weight decay (L2 regularization) is applied. Ilya Loshchilov showed (2018) that Adam has a subtle bug: adding L2 regularization to the loss (loss + λ||θ||²) doesn't apply correctly with Adam because Adam's adaptive learning rate scales the L2 gradient by the same per-parameter factor as the actual gradient. Parameters with large gradients get their weight decay reduced, so popular/active parameters are regularized less. AdamW decouples weight decay from the gradient update: θ ← θ - lr · (adam_step + λθ). The weight decay is applied directly to weights, not through the gradient. For transformers, this matters enormously: embedding matrices and attention weights are updated frequently (large gradient estimates), so Adam-style L2 barely regularizes them. AdamW properly shrinks all weights toward zero. BERT, GPT-2, T5 all use AdamW with weight_decay=0.01 (applied to weight matrices but NOT to biases or LayerNorm parameters).
What is gradient clipping and when is it essential?
Gradient clipping rescales gradients if their global L2 norm exceeds a threshold: if ||∇|| > max_norm, then ∇ ← ∇ × (max_norm/||∇||). This prevents gradient explosion — a problem where a single large gradient step moves weights so far that the model diverges. Essential for: (1) RNNs/LSTMs: gradient magnitudes can grow exponentially through long sequences (the exploding gradient problem). Standard max_norm=5.0. (2) Transformer training at large scale: with 96 layers and 175B parameters, one noisy batch can produce catastrophic gradients. max_norm=1.0 is standard for BERT/GPT. (3) RL training: reward signals can be very spiky. Note: clip_grad_value_() clips each element individually (harsher, less used). clip_grad_norm_() clips the global norm (preserves gradient direction, just scales magnitude).
Explain state_dict(). What does it contain and how do you save/load models correctly?
state_dict() returns an OrderedDict mapping parameter/buffer names to their tensor values. It contains: (1) All learnable parameters (weights, biases) from registered nn.Module layers. (2) Registered buffers (e.g., BatchNorm's running_mean, running_var — not learnable but must be saved). It does NOT contain: the model architecture, optimizer state, epoch number, or loss history. Best practice: save a full checkpoint dict containing model_state_dict, optimizer_state_dict (to resume training), scheduler_state_dict, epoch, best_val_loss. Common mistakes: (a) saving the model directly with torch.save(model, ...) — works but ties the save to the exact class definition path, breaks if you refactor. (b) Using map_location='cpu' or map_location=device when loading — always specify this to prevent CUDA errors when loading a GPU-trained model on a CPU machine.

Chapter 06
Mixed Precision Training (AMP)
Train faster in FP16/BF16 without sacrificing numerical stability

NVIDIA Tensor Cores perform FP16 matrix multiplications 8–16× faster than FP32 on Ampere GPUs (A100, RTX 3090+). Mixed precision training uses FP16 for forward/backward passes and FP32 for weight updates, achieving nearly full speedup with no accuracy loss.

Why FP16 is Dangerous and How GradScaler Fixes It
FP16 range: ~5.96×10⁻⁸ to 65504 FP32 range: ~1.18×10⁻³⁸ to 3.4×10³⁸ Problem: Gradients in a deep network are often < 1×10⁻⁷ → underflow to 0.0 in FP16 → dead gradients → training fails GradScaler solution: 1. Scale loss: loss_scaled = loss × S (e.g., S = 2¹⁶) 2. Backward in FP16: gradients × S (large enough to not underflow) 3. Check for inf/nan in gradients (overflow detection) 4. If clean: unscale gradients (÷S), update weights If dirty: SKIP the optimizer step, reduce S 5. Dynamically adjust S: if no overflows for 2000 steps, double S
AMP Training — torch.cuda.amp
from torch.cuda.amp import autocast, GradScaler

scaler = GradScaler()   # manages loss scaling dynamically

for X, y in train_loader:
    X, y = X.to(device), y.to(device)
    optimizer.zero_grad()

    # Forward pass in FP16 (or BF16 on Ampere GPUs)
    with autocast(device_type='cuda', dtype=torch.float16):
        logits = model(X)             # FP16 compute
        loss   = criterion(logits, y) # FP16 compute

    # Scale loss before backward to prevent FP16 underflow
    scaler.scale(loss).backward()

    # Unscale gradients, check for inf/nan, step if clean
    scaler.unscale_(optimizer)  # optional: allows grad clipping before step
    nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    scaler.step(optimizer)      # skips step if gradients had inf/nan
    scaler.update()             # adjust scale factor for next iteration

# BF16: no GradScaler needed! BF16 has same exponent range as FP32
with autocast(device_type='cuda', dtype=torch.bfloat16):
    logits = model(X)
    loss   = criterion(logits, y)
loss.backward()   # no scaling needed for BF16
optimizer.step()
💡
FP16 vs BF16 — When to Use Which FP16: 5-bit exponent, 10-bit mantissa — high precision but limited range. Needs GradScaler. Available on older GPUs (V100, T4). BF16: 8-bit exponent (same as FP32!), 7-bit mantissa — lower precision but no overflow/underflow risk. No GradScaler needed. Only on Ampere+ (A100, RTX 3090) and TPUs. Rule of thumb: use BF16 if your GPU supports it (simpler, stabler). Use FP16 with GradScaler on older hardware. LLM training (LLaMA, etc.) now standardly uses BF16.

import os

def setup(rank, world_size):
    # Initialize process group (NCCL for GPU-to-GPU, fastest)
    dist.init_process_group(backend='nccl', rank=rank, world_size=world_size)
    torch.cuda.set_device(rank)

    dist.destroy_process_group()

def train(rank, world_size):

    model = MyModel().to(rank)
    model = DDP(model, device_ids=[rank])  # wrap model in DDP

        # Only rank 0 saves checkpoints / logs metrics
        if rank == 0:
            torch.save(model.module.state_dict(), 'checkpoint.pt')

    cleanup()

Custom Losses — Focal Loss & Dice Loss
import torch
import torch.nn as nn
import torch.nn.functional as F

class FocalLoss(nn.Module):
    """
    For severely imbalanced classification.
    Down-weights easy examples, focuses on hard ones.
    FL(p_t) = -(1 - p_t)^γ · log(p_t)
    γ=0: standard CE. γ=2: standard focal loss setting.
    """
    def __init__(self, gamma=2.0, alpha=None, reduction='mean'):
        super().__init__()
        self.gamma = gamma
        self.alpha = alpha  # per-class weight (tensor of size C)
        self.reduction = reduction

    def forward(self, logits, targets):
        # logits: (B, C), targets: (B,)
        log_probs = F.log_softmax(logits, dim=-1)
        probs     = log_probs.exp()

        # Gather probabilities of the true class
        p_t = probs.gather(1, targets.unsqueeze(1)).squeeze(1)

        # Focal weight: (1 - p_t)^gamma
        focal_weight = (1 - p_t) ** self.gamma

        # NLL loss for true class
        loss = -log_probs.gather(1, targets.unsqueeze(1)).squeeze(1)
        loss = focal_weight * loss

        if self.alpha is not None:
            alpha_t = self.alpha[targets]
            loss = alpha_t * loss

        return loss.mean() if self.reduction == 'mean' else loss.sum()


class DiceLoss(nn.Module):
    """
    For segmentation — optimizes overlap directly.
    Dice = 2|A∩B| / (|A| + |B|)
    DiceLoss = 1 - Dice
    Better than BCE for imbalanced foreground/background.
    """
    def __init__(self, smooth=1e-6):
        super().__init__()
        self.smooth = smooth

    def forward(self, preds, targets):
        # preds: (B, 1, H, W) sigmoid output, targets: (B, 1, H, W)
        preds   = F.sigmoid(preds).view(-1)
        targets = targets.view(-1).float()
        intersection = (preds * targets).sum()
        dice = (2 * intersection + self.smooth) / (preds.sum() + targets.sum() + self.smooth)
        return 1 - dice


class ContrastiveLoss(nn.Module):
    """
    For metric learning / siamese networks.
    Pulls similar pairs together, pushes dissimilar apart.
    L = y·d² + (1-y)·max(0, margin - d)²
    """
    def __init__(self, margin=1.0):
        super().__init__()
        self.margin = margin

    def forward(self, emb1, emb2, label):
        # label: 1=similar, 0=dissimilar
        distance = F.pairwise_distance(emb1, emb2)
        loss = label * distance**2 + (1 - label) * F.relu(self.margin - distance)**2
        return loss.mean()
🎯 Interview Q&A — Advanced PyTorch
What is the difference between DataParallel and DistributedDataParallel? Why is DDP always preferred?
DataParallel uses Python threads (limited by GIL) in a single process. It replicates the model on all GPUs, sends a batch slice to each, collects gradients on GPU 0, updates there, then broadcasts updated weights. GPU 0 is overloaded — it handles all gradient reduction and weight updates for all GPUs. Memory imbalance: GPU 0 often runs out first. DistributedDataParallel uses one Python process per GPU (true parallelism, no GIL). Gradients are synchronized via AllReduce (ring allreduce) — each GPU communicates only with its neighbors in a ring topology, distributing the communication load evenly. After allreduce, every GPU has the average gradient and updates identically. DDP advantages: (1) No GPU 0 bottleneck, (2) Each GPU has the same memory usage, (3) Works across multiple nodes/machines, (4) NCCL backend uses NVLink/InfiniBand for near-hardware-speed communication. Rule: always use DDP, even for a single machine with multiple GPUs.
Explain mixed precision training. What does the GradScaler do exactly?
FP16 Tensor Cores are 8-16× faster than FP32 on modern GPUs. But FP16's limited range (min ~6×10⁻⁸) causes gradient underflow — many backward-pass gradients are smaller than this and become exactly 0.0 in FP16, killing training. GradScaler solves this by: (1) Before backward: multiply the loss by a large scale factor S (typically 2¹⁶=65536) — this magnifies all gradients by S, pushing them above FP16's minimum. (2) Backward pass runs in FP16 with inflated gradients. (3) Before optimizer step: divide gradients by S to restore true magnitudes (and convert to FP32 for the update). (4) Check for inf/nan: if scaling caused overflow (gradient became inf in FP16), skip the optimizer step entirely and halve S. (5) If no overflow for 2000 steps, double S (adaptive). The weight master copy is kept in FP32. BF16 (bfloat16) has the same exponent width as FP32, so no underflow/overflow — no GradScaler needed, simpler.
Walk me through implementing a custom focal loss. Why is it better than cross-entropy for class imbalance?
Standard cross-entropy treats all samples equally: -(log p_t). For a 99:1 class imbalance, 99% of the loss comes from the majority class, and the model learns to predict majority class for everything. Focal Loss adds a modulating factor (1-p_t)^γ: -(1-p_t)^γ · log(p_t). When the model correctly classifies an easy majority-class sample with p_t=0.95, the weight is (1-0.95)²=0.0025 — this sample barely contributes to loss. When the model struggles with a minority-class sample (p_t=0.1), weight is (1-0.1)²=0.81 — this sample contributes heavily. γ=2 is standard; γ=0 recovers CE. Implementation: compute per-sample CE loss, gather p_t for true class, multiply by (1-p_t)^γ, average. The key PyTorch detail: work with log_softmax + gather rather than softmax directly — numerically stabler.

🎯 Final Rapid-Fire Q&A
You notice your GPU memory keeps growing during training. What are the likely causes?
Five causes in priority order: (1) Accumulating loss tensor history: doing train_loss += loss instead of train_loss += loss.item() keeps the entire computation graph alive for every batch. Fix: always .item() when accumulating scalars. (2) No torch.no_grad() in validation loop: PyTorch builds computation graphs even in eval() unless explicitly disabled. Fix: always wrap val loop in with torch.no_grad(). (3) Growing lists of tensors: appending GPU tensors to a list (all_predictions.append(logits)) keeps them all in VRAM. Fix: .cpu().numpy() before appending. (4) Hooks not removed: forward/backward hooks registered but never removed accumulate references to activations. Fix: always remove() hooks when done. (5) KV Cache in LLMs: if implementing transformers, the KV cache grows linearly with sequence length. PagedAttention (vLLM) addresses this.
What is FSDP and when should you use it over DDP?
FSDP (Fully Sharded Data Parallel) shards model parameters, gradients, and optimizer states across all GPUs — unlike DDP which keeps a full copy of model + optimizer on every GPU. For a 7B parameter model in FP32 (28GB): DDP requires 28GB + optimizer states (~56GB for Adam) = ~84GB per GPU — impossible on 80GB A100s. FSDP shards everything: with 8 GPUs, each holds 28/8=3.5GB of parameters. Parameters are all-gathered before each forward/backward computation, then resharded. Use FSDP when: model + optimizer state doesn't fit in per-GPU VRAM with DDP (typically models >1B parameters). DDP is simpler and faster for models that fit. FSDP is essential for training LLMs (7B+). PyTorch 2.x: use FSDP2 (DTensor-based) for cleaner API and better performance.
